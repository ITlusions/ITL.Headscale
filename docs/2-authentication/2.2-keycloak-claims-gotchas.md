# 2.2 Keycloak claims gotchas

This is the single most expensive lesson from building this chart - written in detail so it isn't rediscovered the hard way by the next app that needs group-based authorization against this realm's Keycloak.

## The core problem

**The `KeycloakOIDCClient` CRD (Keycloak Operator) creates clients with ZERO protocol mappers by default.** No `groups` claim, nothing - confirmed via `kcadm.sh get clients/<id>/protocol-mappers/models` returning `[]` on a freshly-created client. Any app expecting a `groups` claim (or any custom claim) silently gets no group information at all, with no error at creation time - the failure only shows up later, as an authorization rejection that looks like a user/group-membership problem when it's actually a missing-mapper problem.

## The real failure sequence hit building this (2026-10-24)

A real user, correctly added to `/vpn-users` in Keycloak, kept getting `"authenticated principal is not in any allowed group"` from Headscale. In order:

1. **First suspected cause (wrong): stale group membership or caching.** Ruled out - the user's membership was confirmed correct in the admin console.
2. **Actual root cause #1: the `headscale` client had no protocol mappers at all.** Confirmed via `kcadm.sh get clients/<id>/protocol-mappers/models` → `[]`. Fixed by adding a `groups` claim mapper directly to the client's own dedicated scope (see below for the exact command - the only mechanism that reliably worked).
3. **Still failed after that fix.** Root cause #2, found via `evaluate-scopes/generate-example-id-token` (not guessed): the new mapper's `full.path` setting was `false`, producing `"groups": ["vpn-users"]` - no leading slash. Headscale's `oidc.allowedGroups` was configured as `/vpn-users` - with the slash. Exact string mismatch, case-sensitive, slash-sensitive.
4. **Fixed** by updating the mapper's `full.path` to `true` via `kcadm.sh update clients/<id>/protocol-mappers/models/<mapperId>` - a normal, reliably-working resource update (unlike the broken association-endpoint PUTs described below). Verified via a second `evaluate-scopes` call showing `"groups": ["/itl-cluster-admin", "/vpn-users"]`, then confirmed end-to-end with a real device login.

## The only mechanism that reliably works: dedicated scope, direct POST

Adding a mapper to a client's own built-in dedicated scope, via a plain POST:

```bash
kcadm.sh create clients/<client-id>/protocol-mappers/models \
  -r itlusions \
  -s name=group-membership-as-groups \
  -s protocol=openid-connect \
  -s protocolMapper=oidc-group-membership-mapper \
  -s 'config."claim.name"=groups' \
  -s 'config."full.path"=true' \
  -s 'config."id.token.claim"=true' \
  -s 'config."access.token.claim"=true' \
  -s 'config."userinfo.token.claim"=true'
```

This worked every time it was used: for `headplane_role` and `groups` on the `headplane` client, and `groups` on the `headscale` client.

## What does NOT work: shared client scopes

A shared `headplane-role` client scope (still declared in `ITL.Keycloak.Tenants/files/realm-config/itlusions-shared.yaml` for documentation/history only - not the live mechanism) was tried first, as the more "declarative" approach. The scope and its mapper created fine. Attaching it to a client never worked, across every variant tried:

- `kcadm.sh update clients/<id> -s defaultClientScopes=[...]` - `defaultClientScopes` turned out to be read-only on the client's main representation.
- `kcadm.sh update clients/<id>/default-client-scopes/<scopeId>` (the dedicated association endpoint) - `kcadm.sh update` does a GET-merge-PUT cycle that doesn't work against this bodyless association endpoint. Every variant (full update, sub-resource PUT with `-f`, with `--no-merge`/`-n -b "{}"`) reported exit 0 success but had zero actual effect, confirmed via re-verification each time.
- Doing it by hand in the Keycloak admin console - also failed.

Conclusion: don't attempt shared-scope attachment via `kcadm.sh` or the admin console for this realm/version. Use the dedicated-scope POST method above instead.

## Full-path vs bare group name

`oidc-group-membership-mapper`'s `full.path` config flag: `false` → bare group name (`"vpn-users"`), `true` → full path with leading slash (`"/vpn-users"`). Whatever the consuming app expects, the mapper must match **exactly** - there's no normalization on either side.

## `headplane_role` vs `groups`: a known, accepted mismatch

Headplane's `headplane_role` mapper outputs the group's bare name (e.g. `"platform-admins"`) as the claim value, but Headplane's `role_claim` config expects one of its own fixed enum strings (`admin`, `network_admin`, `it_admin`, `auditor`, `viewer`, `member`) - `"platform-admins"` is not `"admin"`. An attribute-based mapper (reading a per-group `headplane_role` attribute instead of the group's own name) was tried and reverted 2026-10-24 at the user's explicit request, back to the simpler group-membership approach. Accepted outcome: Headplane falls back to its `default_role` (`member`) for now. Revisit the attribute-mapper approach later if exact role values start to matter operationally.

## Deliberately no `roles` claim

This realm has no custom realm roles, only Keycloak's own built-in defaults (`default-roles-itlusions`, `offline_access`, `uma_authorization`) - a `roles` claim would just repeat that boilerplate on every token, nothing authorization-meaningful like `groups` actually is here. Declined explicitly, not an oversight.

## If you're building a new app that checks group membership against this realm

Add the `groups` claim mapper to its client's own dedicated scope, by hand, using the POST method above, immediately after the `KeycloakOIDCClient` CR creates the client. It will not exist by default, and there is currently no declarative/CRD-based way to add it (the `KeycloakOIDCClient` CRD's schema has no protocol-mapper field at all, confirmed against the live CRD).
