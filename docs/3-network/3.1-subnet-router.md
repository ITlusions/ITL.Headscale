# 3.1 Subnet router

## Why this exists

The Headscale server itself is just an HTTP coordination endpoint - registering with it makes your device part of the tailnet, but doesn't make anything else reachable. Reaching cluster-internal resources (pod IPs, Services, nodes) or the home LAN (`192.168.1.0/24`) "on the road" needs an actual device inside those networks advertising routes into the tailnet. That's this component: a plain Tailscale client (not Headscale itself) running as a pod, with network access into everything it needs to forward to.

Not the Headscale server pod doubling as this - kept as a separate pod deliberately, for stability/blast-radius reasons (the control plane shouldn't also be a data-plane router).

## What it advertises

From `values.yaml`'s `subnetRouter.advertiseRoutes`:

```yaml
advertiseRoutes:
  - "10.244.0.0/16"   # cluster pod CIDR
  - "10.97.0.0/16"    # cluster service CIDR
  - "10.99.100.0/29"  # node subnet
  - "10.99.99.0/24"   # MetalLB vlan99 pool
  - "10.99.1.0/24"
  - "10.99.2.0/24"
  - "192.168.1.0/24"  # LAN
```

## Enable it, auth key, approval

```yaml
subnetRouter:
  enabled: true
```

Needs a Headscale preauth key (headless pod, can't do an interactive browser OIDC login):

```bash
headscale preauthkeys create --user 1 --reusable --expiration 8760h
# stored in Secret subnet-router-authkey, key authkey
```

Advertising a route is not the same as it being usable - an admin must approve it after the pod registers and advertises:

```bash
kubectl exec -n itl-headscale deploy/headscale -- headscale nodes list-routes
kubectl exec -n itl-headscale deploy/headscale -- headscale nodes approve-routes \
  --identifier <node-id> --routes "10.97.0.0/16,10.244.0.0/16,..."
```

Nothing can be pre-approved from the admin side before the node registers and advertises - `list-routes` is empty until then.

## State storage: a Kubernetes Secret, not a PVC

The official `tailscale/tailscale` image auto-detects it's running in Kubernetes and defaults to storing tailnet state in a Kubernetes Secret (`TS_KUBE_SECRET`, defaults to a Secret literally named `tailscale`) in its own namespace, rather than (or regardless of) any filesystem path set via `TS_STATE_DIR`. An earlier version of this chart used a PVC for state and crash-looped:

```
error setting up for running on Kubernetes: some Kubernetes permissions are missing, please check your RBAC configuration: missing get permission on secret "tailscale"
missing update permission on secret "tailscale"
```

Fixed by dropping the PVC entirely and granting the RBAC this image actually wants - a dedicated `ServiceAccount` + `Role` (get/update/patch/create on the `tailscale` Secret, plus get/create/patch on Events for its own pod, using `POD_NAME`/`POD_UID` downward-API env vars) + `RoleBinding`, all in `templates/subnet-router.yaml`. This is the image's own intended, native pattern when running in Kubernetes - simpler than managing a PVC for this.

## Talos-specific fixes

**`/dev/net/tun`**: mounted via `hostPath` (`type: CharDevice`). Not independently verified as a general Talos guarantee before this - confirmed working in practice on this cluster (`itl-w03`), 2026-10-24.

**Firewall mode - the real blocker found here**: the image's bundled `iptables` binary is `iptables-legacy`, which failed outright against Talos's kernel:

```
iptables v1.8.11 (legacy): can't initialize iptables table `filter': Table does not exist (do you need to insmod?)
```

Talos is `nftables`-only; the legacy `ip_tables` kernel module Talos doesn't load. The pod stayed `1/1 Running` despite this (the failure is logged as a warning, routing just silently doesn't work), so a healthy pod status alone does **not** confirm subnet routing actually functions - check the logs for this specific error. Fixed by forcing `nftables` mode explicitly:

```yaml
env:
  - name: TS_DEBUG_FIREWALL_MODE
    value: "nftables"
```

Deliberately not `auto` - Tailscale's own auto-detection heuristic may still pick `iptables` simply because the binary is present in the image, regardless of whether the kernel actually supports it. Confirmed fixed via the log line changing to `firewallmode="nft-forced"` and no further router-config errors.

A smaller, likely non-fatal warning also appears:

```
router: warning: failed to enable src_valid_mark: sysctl(net.ipv4.conf.all.src_valid_mark=1): open /proc/sys/net/ipv4/conf/all/src_valid_mark: read-only file system
```

Expected in a container (can't write host-wide sysctls without specific Kubernetes sysctl allowlisting) - Tailscale has a built-in connmark-based fallback for exactly this case (logged immediately before the warning: `"enabling connmark-based rp_filter workaround"`). Not something that's been fixed, just understood as non-fatal.

## PodSecurity

The namespace gets `pod-security.kubernetes.io/enforce: privileged` conditionally on `subnetRouter.enabled` (`templates/namespace.yaml`) - the Headscale server pod itself doesn't need this (plain HTTP server), but this pod needs `NET_ADMIN`/`NET_RAW` capabilities, and PodSecurity is enforced per-namespace, not per-pod. Same requirement `ITL.Wireguard` had.

## `hostNetwork`

Set to `true` - removes one NAT layer (pod network → node) for WireGuard's NAT traversal/hole-punching. Tried 2026-10-24 after confirming a real device's connection to this gateway was relayed via DERP instead of direct; did not change the outcome on that occasion (see [4.2](../4-operations/4.2-derp-relay-followup.md) - the actual blocker was almost certainly the test device's own cellular carrier NAT, not anything on this side). Left enabled regardless - it's a genuine improvement to this pod's own network position even if it didn't resolve that specific test, and costs nothing to keep.
