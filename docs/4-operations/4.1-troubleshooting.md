# 4.1 Troubleshooting

Real failures hit building and operating this chart, kept here so they don't get re-diagnosed from scratch.

## Config changes not taking effect after `helm upgrade`

Symptom: a ConfigMap-sourced setting changes, `helm upgrade` reports success, but the running pod's behavior doesn't change. Cause: Kubernetes doesn't restart a pod just because a ConfigMap it mounts changed - the Deployment's pod template itself is unchanged, so no rollout is triggered. Fix: the Deployment needs a `checksum/config` annotation (a hash of the rendered config), so the pod template genuinely changes whenever the config does:

```yaml
annotations:
  checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
```

This exact gap caused a real, repeated SSO failure in `ITL.Headscale.UI` (stale `redirect_uri` pointing at an old hostname across three redeploys, because the pod never restarted on ConfigMap-only changes) before being diagnosed and fixed.

## The Headscale image has no shell at all

`kubectl cp`, `kubectl exec ... sh -c`, anything assuming `sh`/`cat`/`tar` exist inside the container - none of it works against the official Headscale image. `kubectl cp` specifically needs `tar` on both ends, so it fails regardless of how carefully the local-side arguments are constructed. For getting any file-shaped config into a shell-less pod, use a Helm-templated ConfigMap mount instead (see [3.2](../3-network/3.2-acl-policy.md) for the exact pattern used for the ACL policy) - fully declarative, no runtime file transfer needed.

## MSYS/git-bash path mangling (Windows-specific)

`/bin/bash`-style POSIX paths passed to `kubectl exec`/`kubectl run` on a Windows+git-bash setup get silently rewritten into invalid Windows paths, unless prefixed with `MSYS_NO_PATHCONV=1`. The inverse problem: with that env var set, purely-POSIX *local* file paths (e.g. `/tmp/foo`) fail to resolve, since the native Windows `kubectl.exe` doesn't understand them either. The reliable pattern: Windows-style backslash paths for local file arguments, `MSYS_NO_PATHCONV=1` only for remote colon-containing specs - or better, avoid `kubectl cp` entirely (see above) in favor of `kubectl exec -i ... -- sh -c 'cat > file'` for containers that do have a shell, or REST API calls via a throwaway `alpine/k8s` pod for ones that don't.

## `kcadm.sh update` against bodyless association endpoints is unreliable

`kcadm.sh update` does a GET-merge-PUT cycle, which doesn't work against endpoints that represent an *association* rather than a resource (e.g. `clients/{id}/default-client-scopes/{scopeId}`) - every variant tried reports exit 0 success but has zero actual effect. Full detail and the working alternative (POST directly against the client's own dedicated-scope protocol-mappers endpoint) in [2.2](../2-authentication/2.2-keycloak-claims-gotchas.md).

## Dual-domain TLS: both `.com` and `.nl` genuinely resolve

`headscale.itlusions.com` and `headscale.itlusions.nl` both resolve to the same public IP - a pre-existing dual-domain DNS pattern used throughout this org, not a typo or misconfiguration. A client hitting `.nl` when only `.com` had a matching Ingress/cert got Traefik's default self-signed fallback cert, triggering a real "likely intercepted connection" warning. Fixed by adding `.nl` as a second SAN on the same cert (list all hostnames under the same `tls.hosts` array - cert-manager provisions one cert with multiple SANs) plus a second `rules` entry pointing at the same backend Service - see `templates/ingress.yaml`'s `additionalHosts` pattern. If a new public-facing host needs the same treatment, add it to `ingress.additionalHosts` in `values.yaml` rather than hand-rolling a second Ingress resource.

## A healthy pod (`1/1 Running`) doesn't mean the feature works

The subnet-router pod ran as `1/1 Running` for a while with subnet routing silently non-functional (the `iptables`/`nftables` kernel mismatch - see [3.1](../3-network/3.1-subnet-router.md)). Pod health checks the process stayed up, not that its actual job succeeded. Check logs for warnings even on a "healthy" pod when something downstream isn't working as expected.
