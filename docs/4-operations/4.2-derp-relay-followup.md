# 4.2 DERP relay follow-up

**Status: deferred, not started.** Documented 2026-10-24 as a scoped follow-up, deliberately not built the same night it was investigated.

## What was observed

A real device (Android phone, cellular data) connecting through the in-cluster subnet router stayed **relayed** through Tailscale's own Amsterdam DERP server (`derp-14`/`ams`) rather than establishing a **direct** peer-to-peer connection:

```bash
kubectl exec -n itl-headscale deploy/subnet-router -- tailscale status --json
# Peer -> CurAddr: "" (empty - no direct endpoint)
# Peer -> Relay: "ams"
```

`CurAddr` empty + a non-empty `Relay` field means every packet between the phone and the gateway takes a round-trip through that external relay server, instead of going directly.

## What was tried

`subnetRouter.hostNetwork: true` was added to the gateway pod - removes one NAT layer (pod network → node), putting the gateway's own public-facing network identity one step closer to the LAN's actual router/NAT instead of being behind an extra layer of Kubernetes pod-network NAT. Confirmed via logs that this took effect (`magicsock: endpoints changed: 188.213.90.236:... (stun)` - the cluster's real public IP, correctly discovered via STUN). **Did not change the outcome** - the phone stayed relayed after this change too.

## Why it's very likely not fixable from this side

Cellular carriers put large numbers of customers behind a small number of public IPs (CGNAT - carrier-grade NAT), and that NAT is almost universally the restrictive/symmetric kind, one of the hardest types to hole-punch through from either direction. Improving the gateway's own network position (which `hostNetwork` did) only helps if the *other* side's NAT is cooperative - if the phone's own carrier NAT is the blocking factor, no amount of fixing the gateway's side changes the outcome. This matches what was actually observed: a real, concrete improvement to our side's STUN-discovered identity, with zero change in the relay outcome.

**Not yet tested**: the same phone on WiFi instead of cellular. If direct succeeds there but not on cellular, that would confirm the carrier NAT theory conclusively. If it's still relayed on WiFi too, that would point back to something fixable on this side after all (e.g. the home/office router's own NAT type or UPnP support) - worth doing before investing in the self-hosted DERP option below.

## What self-hosting a DERP server would and would NOT fix

**Would NOT fix**: the relay-vs-direct outcome itself. A self-hosted DERP server is still a relay - it doesn't change whether direct peer-to-peer NAT traversal succeeds or fails. If the phone's cellular NAT is the blocker, it stays relayed regardless of whose server is doing the relaying.

**Would fix**: for traffic that stays relayed anyway, a self-hosted DERP server removes the dependency on - and the extra network hop to - Tailscale's external Amsterdam relay. Since this cluster's infrastructure is already Netherlands-based, a self-hosted relay would likely offer a modest latency improvement for relayed traffic, and keeps that traffic inside infrastructure under our control rather than passing through a third party's servers.

## What it would actually take to build

Headscale has this built in - `derp.server` in the config schema, currently `enabled: false`:

1. `derp.server.enabled: true`, a generated DERP server private key, `stun_listen_addr` set.
2. The real public IP/hostname set in the DERP region's `ipv4`/`ipv6` fields.
3. **A new UDP-exposed port** (STUN, typically `3478`) - the same category of problem `ITL.Wireguard` hit originally: raw UDP can't go through Traefik's HTTP(S) proxying, so this needs its own `LoadBalancer` Service via MetalLB, plus the same external-reachability/router considerations as anything else genuinely public-facing on this cluster.

Not a config toggle - real new infrastructure. Scope and build as a separate piece of work when there's a clear reason to (sustained bandwidth-heavy relayed traffic, or a privacy requirement to keep relay traffic off Tailscale's own servers), not purely for the latency win on its own.
